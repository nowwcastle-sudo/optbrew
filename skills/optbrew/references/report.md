# Report packet and evidence contract (v0.1.0)

`node skills/optbrew/scripts/cli.mjs report --input <packet.json> --output-dir <new-directory>` writes `report.json` and `report.md`. It makes no network or paid calls. It refuses to replace an existing report. A report is a local audit artifact; a local passing verification does not establish deployment, indexing, traffic, ranking, citations, or business impact.

`ReportPacket` retains the approved `run_context`, raw `baseline.input`, optional `after.input`, their `score()` results, `compare()` result, metrics, findings, changes, costs, remaining work, and source identity. `evidence_root` points to the run directory. The CLI resolves a relative root against the packet's directory. Each `evidence_index` item has `{ref,sha256,kind,run_id,source_ref?,source_url?}`. Every indexed file is reopened, checked against its SHA-256, and contained by the resolved run directory. The context file at each phase's `run_context.evidence_ref` must contain exactly that run context.

An applicability `evidence_ref` points to JSON `{run_id,target,protocol_hash,approved_by,decisions}`. Each decision is `{scope:"family",family_id,condition,reason}`, `{scope:"url",normalized_url,condition,reason}`, or `{scope:"unit",unit_key,condition,reason}`. A matching record identifies the decision and its approval context; it does not independently prove the underlying site fact. Missing or unrelated decisions are contract errors. Unknown checks remain in the denominator.

Collector phases use `audit_snapshots:[{phase:"baseline"|"after",audit_ref,context_ref}]`, one Task 5 evidence index per phase. A baseline-only packet may use legacy `audit_ref`. The audit's run/context, observation file, collection file, module output, artifact `evidence_ref` and non-null raw body hash must match that phase. A bodyless DNS/timeout artifact has `content_hash:null`, points to the collection file, and remains `unknown`; it is not compared to the collection file hash as though it were a body. Same-URL before/after observations must use their own snapshot and raw ref.

Owner export metrics replay through `normalizeImport()` from evidence JSON `{kind:"native_export",run_id,provider,rows,metadata}`. `run_context.protocol.target_identity` is a comparison-relevant, hashed field. It contains `{target,native_properties:[{provider,property,hostname?,path_prefix?,evidence_ref}],panel?}`. Each native mapping ref points to a run/target/provider/property/approval record. Known row hostname and path must fit its approved mapping. The native metadata supplies `collected_at` with offset and `last_complete_date` in the report timezone; a pair needs complete, adjacent 28-day windows, identical definition, provider definition, full sample selection, filters, panel and timezone. Missing completeness or a changed cohort yields no delta. Imported provider origin and completeness remain attributed to the owner's export.

AI panel metrics replay through `measurePanel()` from `{kind:"panel",run_id,provider_origin,panel,responses,evaluations}`. Frozen `target_identity.panel` is `{target_entity,target_domains,competitor_entities,evidence_ref}` and has a matching approved mapping file. Questions, engine, surface, model, search use, locale, region and target identity must match the frozen run. Every response has `response_ref` (indexed redacted provider response) and `extraction_ref` (indexed `{run_id,response_id,raw_ref,raw_sha256,normalized_response}` receipt). Every evaluation has `evidence_ref` for an indexed `{run_id,response_id,approved_by,evaluation}` receipt. Evaluable citations have `source_evidence_ref` whose index entry `source_url` equals the cited URL. Evaluable claims have `fact_id` and `source_evidence_ref`, and their `panel.fact_list_ref` opens an approved `{run_id,target_entity,approved_by,facts:[{fact_id,...}]}` list. Missing material is a contract error. These links preserve attribution; they do not independently authenticate a provider or prove factual truth.

The persisted `CostLedger` snapshot is indexed at `costs.evidence_ref`; unknown settlement, observed overrun and `host_policy` limitations stay visible. Do not include secrets, account tokens, personal records, or private card text in a packet or evidence directory.

Findings merge only when check, unit and normalized problem text agree. Every contributing source remains on the merged finding. A finding must match a failed or unknown check observation. The curated remediation catalog chooses only an applicable, directly relevant mechanism; official sources lead the evidence order. A remote finding has a proposed change location and validation method but remains `proposed_only`. A `ChangeRecord` receipt binds run ID, change ID, target, path, environment, after hash, status, and passing checks whose indexed changed bytes have that hash. Production also requires a deployment receipt for the same target/path/hash and an explicitly linked passing `after` observation. Every required linked change must pass; local pass plus production pending remains pending. Receipts and hashes establish this local evidence chain, not external deployment truth. No SEO gain is predicted. Hypothetical readiness changes belong in a separately marked scenario, never in `after`.

For `verification.status:"passed"`, the indexed receipt has `{run_id,change_id,target,path,environment,after_hash,status,checks:[{id,status:"passed",observed,evidence_ref,after_hash}]}`. Each check's ref opens the changed bytes. Production adds `deployed:true`, `deployment:{target,path,after_hash,evidence_ref}`, and `observation_id` / `observation_evidence_ref` in both receipt and `ChangeRecord.verification`. The deployment evidence file repeats run, target, path, hash, environment `production` and `confirmed_by`. The matching `after` observation must resolve the linked finding in a run context with the same target and `production` environment. Its indexed evidence entry also identifies `phase:"after"`, that target and `environment:"production"`; absent or different attribution leaves the finding unverified. Other comparison-condition changes may still yield `not_comparable` without invalidating a same-target verification. A pending receipt cannot combine with another passed change to finish a finding.

Collector verdicts are replayed, not trusted. For each collector-sourced `index-policy`, `document-title` and `search-crawl-policy` observation the report reopens the preserved raw bytes of the same phase and rebuilds the verdict with the code the audit used. Index directives come from the HTML `<head>` meta tags (comments and script, style, textarea and title text are ignored) and the collected `X-Robots-Tag` header. The generic `robots` directives combine with the target engine's own (`googlebot` for Google, `yeti` for Naver); a header prefixed with another crawler name does not apply, and a crawler prefix scopes only the header line that carries it. Meta directives may be separated by commas or semicolons. A robots meta tag inside `<template>` or `<noscript>` is conservatively counted as a noindex directive. A present title replays as `unknown` because uniqueness and descriptiveness need separate evidence; a missing title replays as `fail`; reviewed duplicate-title or semantic verdicts from other evaluators are not rejected for having a title. A crawl-policy verdict needs the declared `robots` auxiliary artifact, its content hash, the page's final URL and a target engine, then recomputes `pass` or `fail` from the robots bytes. Every collected response is replayed from its hashed `*.response.json` record: the collection entry must equal the record, the final URL must follow the recorded redirect chain (no redirect means the final URL is the normalized request URL), and header lines come from the record, so index every `responses[].evidence_ref` from the audit index with `source_ref:"optbrew:collector"`. A selected page must be either collected or listed in `skipped`, and an indexed collector artifact requires its baseline audit snapshot. Every observation the collector plans for a selected page (fetch, title, index and, for Naver with a disallowing declared robots file, crawl policy) must be present in the packet and in the saved observations; a missing one is an error, never a silent pass. A redirected URL binds its requested unit to the artifact first; the module output must describe that artifact's final URL (`requested_url` and `redirect_chain` stay with it). A header-only `noindex` finding uses the same HTML plus header replay as the observation and must belong to the finding's own unit.

`verified_local` uses the production binding: the change and its receipt name an `observation_id` and `observation_evidence_ref` for a passing after observation that the collector produced (so the audit replay covers it); that raw evidence entry is labelled `phase:"after"`, `environment:"local"` and the run target, and the after context is `local` for the same target. A byte-hash receipt or an agent-written observation alone leaves the finding `modified_unverified`. For `verified_production` the finding carries `resolution` (observation ID, evaluator type, source) and the Status cell reads `resolved by <evaluator_type> observation from <source_ref>`, so a model-attested resolution is visibly distinct from a collector-verified one; the production gating rules are unchanged. Native path mappings match whole path segments: the exported path starts with a single `/` (protocol-relative paths and absolute URLs on another host are refused) and equals the approved `path_prefix` or continues after a `/`.

Both formats show four tables: score, remediation, actual outcomes, and remaining work. Score arithmetic comes from `score()` and `compare()`. Actual outcome pairs require the same native metric definition, filters, sample selection and panel, plus two adjacent complete 28-day windows. An absent or ambiguous value stays unknown. Markdown escapes pipes, HTML and line breaks in evidence and titles. `data_class:synthetic` labels fixture reports and cannot be presented as observed production performance.
