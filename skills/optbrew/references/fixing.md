# Fixing local files

SKILL.md 10단계가 쓰는 문서다. 사용자가 보고서의 고칠 것을 고치라고 말했을 때만 연다. `<SKILL_DIR>`과 `<OUT>`은 SKILL.md와 같다.

## 고치기 전에 스스로 묻는다

- 이 파일은 사용자가 고치라고 한 문제의 원인인가? 증상이 보이는 파일과 원인 파일은 다를 수 있다. 제목이 틀린 쪽은 보통 그 쪽의 HTML이 아니라 제목을 만드는 템플릿이나 설정에서 고친다. 템플릿 하나를 고치면 같은 틀의 쪽이 모두 바뀌므로 영향받는 쪽 전부(`fixes.md`의 목록)를 먼저 본다.
- 고친 값은 사이트가 스스로 보여 주는 사실과 맞는가? 구조화 데이터, 제목, 설명에 쓰는 이름·전화·주소는 공개 화면에 보이는 값이어야 한다. 화면에 없는 값을 마크업에만 넣으면 검색엔진의 구조화 데이터 지침에 어긋나 마크업이 무시되거나 제재를 받을 수 있고, 이 감사의 `structured-data-truth` 검사도 다시 실패한다([policies.md](policies.md)).
- 이 수정이 다른 목표를 해치지 않는가? `noindex`를 지우는 일, robots.txt에서 크롤러를 여는 일은 일부러 막아 둔 쪽까지 열 수 있다. 사용자가 그 쪽이 검색에 나와야 한다고 확인한 뒤에만 한다.
- 이 파일을 지금 고칠 권한이 있는가? 사용자가 승인한 파일만 고친다. 운영 서버의 파일, 빌드가 만든 파일(`dist/`, `build/`, `.next/` 등)은 고치지 않는다. 빌드가 다시 덮어써서 고친 것이 사라진다. 그 원본 소스를 찾는다.

## 순서

1. 고칠 소스 폴더를 사용자에게 묻는다. 원격에만 있는 사이트면 고치지 않는다. 각 문제의 수정안과 적용·확인 방법만 `proposed_only`로 낸다.
2. 고치기 전에 원인을 찾는다. [source-analysis.md](source-analysis.md)대로 2단계에서 찾은 도구를 먼저 쓴다. 도구가 없으면 직접 읽고, "소스 분석 도구가 없어 직접 읽어 찾았습니다. 놓친 곳이 있을 수 있습니다."라고 한 줄 알린다.
3. 고칠 파일마다 고치기 전에 변경을 시작한다. 승인받은 파일만 고친다.

```
node "<SKILL_DIR>/scripts/cli.mjs" change start --out "<OUT>" --root "<소스 폴더>" --path "<고칠 파일>" --finding "<finding_id>"
```

   - 이 명령이 파일을 `<OUT>/changes/backup/<change_id>-<파일 이름>`에 한 번만 복사하고, 복사한 바이트의 해시를 `<OUT>/changes/pending/<change_id>.json`에 적는다. 백업은 소스 폴더 안에 만들지 않는다. 소스 폴더 안의 백업은 사이트와 함께 배포되거나 빌드에 섞일 수 있다.
   - `--path`는 소스 폴더 안의 파일이다. 상대 경로는 소스 폴더에서 읽는다. `..`로 나가는 경로, 링크를 따라가면 소스 폴더 밖이 되는 경로, 파일이 아닌 경로는 거절한다.
   - `--finding`은 `fixes.md`에서 고칠 것의 제목인 `finding_id`다. 이 파일을 고치는 문제가 여럿이면 `--finding`을 문제마다 붙인다. 결과 폴더에서 파일 하나의 변경 기록은 하나이므로, 같은 파일에 시작했거나 끝낸 변경이 있으면 거절한다. 그래서 한 파일의 문제는 한 번에 모아 시작한다.
   - 마지막 줄 JSON의 `change_id`(`c1`, `c2`)를 읽어 둔다.
4. 파일을 고친다.
5. 고친 뒤 변경을 끝낸다.

```
node "<SKILL_DIR>/scripts/cli.mjs" change finish --out "<OUT>" --path "<고친 파일>" --tool "<쓴 도구 이름>" --query "<도구에 한 질의>"
```

   - 이 명령이 지금 파일의 해시를 구해 `ChangeRecord`를 `<OUT>/changes/<change_id>.json`에 쓰고 대기 파일을 지운다. 해시 명령도 JSON도 손으로 쓰지 않는다. 손으로 쓴 기록은 계약 검사를 지나지 못하고, 백업과 같은 바이트인지 아무도 확인하지 않는다. 파일이 시작할 때와 같으면 거절한다.
   - 백업이 없거나 시작할 때와 다르면 거절한다.
6. `analysis`는 [source-analysis.md](source-analysis.md)의 기록 규칙대로 `change finish`의 옵션으로 채운다. `--tool`(쓴 도구마다)과 `--query`(질의마다)는 여러 번 쓸 수 있고, 질의가 `-`로 시작하면 `--query=<질의>`로 쓴다. `--tool` 없이 끝내면 `self_analysis`가 `true`로, `--tool`을 쓰면 `false`로 기록된다. 도구를 쓰고도 직접 읽어서 원인을 찾았으면 `--self-analysis`를 더한다.
7. 사용자에게 한 줄 알린다: 보고서는 이 변경 기록을 읽지 않는다. 기록은 사용자가 무엇을 고쳤는지 보관하는 용도다. `backup_ref`와 `evidence_ref`는 파일 경로이며 증거 저장소의 참조가 아니다. 다시 확인(11단계)해도 `verification`은 갱신되지 않고 `pending`으로 남는다. 고친 것을 되돌리려면 `backup_ref`의 사본을 원래 경로에 복사한다.
8. 수정안은 [routing.md](routing.md)에서 맞는 가이드 하나를 골라 근거로 삼는다. 고른 가이드만 열고 `modules/` 아래 다른 파일은 열지 않는다. 가이드가 길면 그 문제에 맞는 절만 읽는다. 정책 해석과 제출 권한은 [policies.md](policies.md)를 따른다.
9. 모든 파일을 끝낸 뒤 SKILL.md 11단계로 간다.
