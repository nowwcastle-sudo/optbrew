# Intake and start questions

SKILL.md의 3단계~6단계가 쓰는 참고 문서다. 순서는 SKILL.md가 정한다. 4단계의 시작 질문 틀과 항목별 쓰는 법은 이 문서에만 있다.

## 원칙

- 사용자가 이미 준 값은 다시 묻지 않는다. 주소가 없을 때만 주소 하나를 따로 묻는다. 나머지는 시작 질문 한 묶음에서 묻는다.
- 모르는 값은 `unknown`으로 남긴다. 값을 지어내지 않는다.
- 소유자 자료(검색 콘솔 내보내기)나 유료 API가 없어도 허용된 공개 HTTP/HTML로 기본 감사는 끝까지 간다. 없는 자료는 보고서의 남은 일이 된다.
- 원격 전용 사이트는 수정할 수 있다고 가정하지 않는다.
- 비용이 드는 호출은 이 흐름에 없다. 유료 경로는 예상 단가의 출처·날짜, 승인된 한도, 중단 조건이 기록되기 전에는 쓰지 않는다. 단가를 모르면 0으로 넣지 말고 보류한다.
- 감사 범위(주소 범위, 요청 수, 렌더할 쪽, 판정 대상)는 `run.mjs`가 답 파일에서 `RunContext`와 프로토콜로 만든다. 에이전트가 계약 JSON을 손으로 조립하지 않는다.

## `start.json`을 읽는 법

`preflight.mjs`가 `<OUT>/preflight/start.json`에 쓴다. 채점하지 않는 사전 읽기이며, 본 감사의 요청 수와 프로토콜에 들어가지 않는다. 본 감사는 답 파일로 프로토콜을 고정한 뒤 처음부터 새로 수집한다.

| 필드 | 뜻 | 쓰는 곳 |
|---|---|---|
| `probe.harness` | 실행 환경: `claude-code`, `claude-code-cloud`, `codex`, `other` | 키 저장 런북 고르기 |
| `probe.block_reason` | `null`, `site_down`, `codex_sandbox`, `cloud_network_level` | 3단계 표 |
| `probe.transport`, `probe.address_vetting`, `probe.proxy` | 직접 연결인지 프록시인지. 프록시는 호스트와 포트만 있다 | 답 파일에 그대로 복사 |
| `probe.chrome` | `{ found, kind, reason }`. 없으면 렌더 항목이 빈칸이 된다 | 답 파일에 그대로 복사 |
| `probe.google_key` | Google 키 유무. 값은 없다 | 답 파일에 그대로 복사 |
| `sitemap_pages`, `sitemap_pages_basis` | 사이트맵 쪽수. `basis`는 `exact`, `lower_bound`, `null` | 「표본」 설명 |
| `max_urls_raise` | "상한을 올림"일 때 답 파일의 `max_urls`. `null`이면 「표본」 항목을 보내지 않는다 | 「표본」 항목, 답 파일 |
| `question_candidates_input` | 읽은 쪽마다 `{ url, title, h1, description }` | 「질문」 항목 |
| `fact_candidates` | `{ key, value, source_url }`. 쪽에서 읽은 이름·주소·전화·설립 연도 후보 | 「사실」 항목 |
| `start_runbooks.blocking` | 감사가 돌지 않게 막는 런북. 최대 1개. `text`에 본문이 들어 있다 | 3단계 표 |
| `start_runbooks.improving` | 있으면 결과가 채워지는 런북. 각각 `{ id, line, harness }`. 지금 목록에서는 3개까지 | 「준비」 항목 |

`probe`는 한 번만 점검한다. 답 파일에는 `start.json`의 `probe`를 그대로 복사한다. 사용자가 점검 뒤에 키나 크롬을 준비했으면 점검 명령을 다시 실행해 새 `start.json`을 쓴다.

## 시작 질문 보내기

한 메시지로 보낸다. 항목의 순서를 바꾸지 않는다. 항목마다 기본값을 적는다. 사용자가 처음부터 "간단히"라고 했으면(3단계에서 `--level brief`를 붙였으면) 「안내 수준」의 `(기본)`을 "간단히" 쪽에 붙인다. 틀의 각 항목에는 이름(「안내 수준」, 「주소와 목표」, 「질문」, 「사실」, 「표본」, 「준비」)이 있다. 빠지는 항목이 있으면 남은 항목에 1부터 번호를 다시 붙인다. 사용자가 답한 번호는 이 메시지의 번호이므로, SKILL.md 5단계는 그 번호를 항목 이름으로 되짚어 읽는다.

```
감사를 시작하기 전에 한 번만 확인합니다. 번호마다 답하셔도 되고, 괜찮으면 '시작'만 답하셔도 됩니다. '시작'은 아래 기본값을 모두 받아들인다는 뜻입니다.

1. 안내 수준: 단계별로 자세히 (기본) / 간단히
2. 주소와 목표: <주소> / 목표: <목표 후보>
3. 사람들이 찾을 질문 <개수>개 (틀린 것만 알려 주세요):
   <번호. 질문 — 브랜드/일반>
4. 사이트에서 읽은 사실 (틀린 것만 알려 주세요):
   <종류: 값 (읽은 페이지)>
5. 사이트맵에 <N>페이지가 있습니다: 표본 50페이지 (기본) / 상한을 올려 최대 200페이지 (robots·sitemap 요청도 함께 세므로 모든 페이지가 들어가지 않을 수 있습니다)
6. 있으면 결과가 더 채워지는 것 (원하는 것의 말만 답하세요):
   <improving 항목의 line을 한 줄씩>

준비를 못 한 항목이 있어도 감사는 끝까지 갑니다. 빠진 칸은 보고서의 '남은 일'에 방법과 함께 적힙니다. 답을 받기 전에는 아무것도 실행하지 않습니다.
```


이 메시지가 그 턴의 마지막 메시지다. 보낸 뒤 진행 문장이나 요약을 쓰지 않고 턴을 끝낸다. 런북 본문은 이 메시지에 넣지 않는다. 사용자가 "키", "크롬", "내보내기"처럼 답할 때만 SKILL.md 5단계에서 보여 준다.

### 「안내 수준」

런북의 깊이다. 답 파일의 `guidance_level`이 `beginner` 또는 `brief`가 된다.

### 「주소와 목표」

주소는 확인만 받는다. 목표는 사용자가 이미 말한 것이 기본이다. 고를 수 있는 목표는 검색 유입, 네이버 노출, AI 답변 인용, 브랜드 사실 정확성, 전환이다. 사용자의 말이 이 중 하나를 가리키면 그 목표 이름으로 보여 준다. 문의, 예약, 상담, 전화는 전환이다. 답 파일에는 이 목표 이름을 그대로 적는다. 실행은 `scripts/core/goals.mjs`의 낱말표로 목표 이름을 읽어 점검할 엔진과 항목을 정한다. 사용자가 목표를 말하지 않았으면 "검색 유입", "AI 답변 인용"을 기본으로 둔다.

### 「질문」

감사가 "이 사이트가 이 질문에 답하는가"를 보는 기준이다. `question_candidates_input`의 제목, 첫 제목, 설명에서 만든다.

질문을 만들기 전에 스스로 묻는다.

- 이 사이트를 모르는 사람이 검색창이나 AI에 실제로 칠 문장인가? 사이트의 메뉴 이름("사업안내")이 아니라 사람의 말("비용은 얼마인가요")로 쓴다.
- 목표마다 질문이 하나 이상 있는가? 전환이 목표면 신청·예약·문의 방법을 묻는 질문, 브랜드 사실 정확성이 목표면 위치·연락처·운영 시간을 묻는 질문을 넣는다.
- 답이 이 사이트 안에 있어야 하는 질문인가? 경쟁사 비교나 업계 통계처럼 사이트가 답할 이유가 없는 질문은 「찾지 못함」만 늘리고 고칠 것을 만들지 않는다.
- 질문끼리 겹치지 않는가? 말만 다른 같은 질문은 보고서의 질문표에서 같은 줄을 두 번 채울 뿐이고, 그만큼 다른 의도의 질문이 빠진다.

- 10개 안팎으로 만든다. 8개에서 12개 사이면 된다.
- 브랜드 질문(이름이 들어간 질문, 예: "OO는 어디에 있나요")과 일반 질문(이름 없이 찾는 질문, 예: "재가 요양 서비스 신청은 어떻게 하나요")을 섞는다.
- 사이트의 언어로 쓴다. 사이트에 근거가 없는 주제로는 만들지 않는다.
- 답 파일에서는 `{ id, question, category, goal }`이다. `id`는 `q1`, `q2`처럼 번호를 붙인다. `category`는 `brand` 또는 `non_brand`다. `goal`은 「주소와 목표」에서 확정한 목표 중 하나다.

### 「사실」

`fact_candidates`를 `종류: 값 (읽은 페이지)`으로 보여 준다. 후보가 없으면 이 항목을 뺀다. 쪽 사이의 사실 일치(이름, 주소, 전화, 설립 연도)를 검사하는 기준이다. 후보는 사이트에서 읽은 값이므로, 이 목록은 "사이트가 자기 자신과 맞는가"를 보는 용도다. 사이트 밖 진실을 확인하지 않는다. 사용자가 틀린 값을 고치면 고친 값을 쓴다.

### 「표본」

`start.json`의 `max_urls_raise`가 `null`이 아닐 때만 넣는다. 사이트맵이 50을 넘거나 쪽수가 하한값(`sitemap_pages_basis`가 `lower_bound`)일 때 그렇다. `null`이면 뺀다. 기본 상한은 50쪽이다(`max_urls_default`). 올릴 수 있는 한도는 200쪽이다(`max_urls_cap`). 두 값의 원천은 [limits.json](limits.json)이다. 상한은 페이지와 보조 파일(robots, sitemap)의 요청 수를 모두 합친 값이다. 쪽이 다른 주소로 넘어가면 요청이 하나 더 든다. 그래서 상한 안에 여유가 남는다(`redirect_reserve`: 쪽의 10%, 최소 2). 이 여유는 선택한 쪽과 보조 파일이 상한 때문에 빠지지 않게 한다. 그래서 상한을 올려도 모든 쪽이 들어가지 않을 수 있다. 질문에 이 말을 함께 적는다.

### 「준비」

`start_runbooks.improving`의 `line`을 고치지 않고 한 줄씩 그대로 넣는다. 항목이 없으면 뺀다. 지금 목록에서는 세 항목(Google 키, 크롬, 내보내기)까지만 나온다. 사용자가 해당 단어로 답할 때만 런북을 펼친다. 답하지 않으면 감사는 그대로 가고, 그 런북은 보고서의 남은 일에 붙는다.

## 답 파일의 필드

`<OUT>/intake-answers.json`의 필드는 SKILL.md 6단계가 보여 준다.

| 필드 | 뜻 |
|---|---|
| `schema_version` | [versions.json](versions.json)의 `contract_schema` 값 |
| `guidance_level` | 런북 깊이: `beginner`, `brief` |
| `url` | 사용자가 확인한 감사 시작 주소 |
| `goals` | 목표 문자열 목록 |
| `questions` | 확정한 질문 목록 |
| `facts` | 확정한 사실 목록 |
| `sample_mode` | `null`, `sample`, `raise`. 「표본」 항목을 보내지 않았으면 `null` |
| `max_urls` | 요청 상한. 정수이며 기본 50. `raise`이면 `start.json`의 `max_urls_raise`(200 이하) |
| `source_tools` | 소스 분석 도구 이름 목록 |
| `probe` | `start.json`의 `probe` |
| `owner_exports` | 선택. 사용자가 내려받은 파일 목록 `{ kind, path }`. `kind`는 `gsc`(Search Console) 또는 `naver`(네이버 서치어드바이저). 받은 것이 없으면 필드를 뺀다 |

## 재개

같은 결과 폴더의 증거와 답 파일을 읽어 이어간다. 새 실행으로 조용히 바꾸거나 증거를 덮어쓰지 않는다. 목표, 범위, 표본이 바뀌면 새 결과 폴더에서 처음부터 한다. 이전 결과와 비교할 수 있는지는 비교 단계가 판정한다.
