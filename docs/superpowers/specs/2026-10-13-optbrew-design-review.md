# optbrew 설계 자체 검토

검토일: 2026-10-13, Asia/Seoul.
대상: 2026-10-13-optbrew-design.md와 2026-10-13-optbrew-sources.md.
검토 종류: 작성자의 설계 자체 검토. 독립적인 사용자 평가와 제품 실행 시험은 아니다.

## 1. 확인한 계약

| 영역 | 결과 | 근거 |
|---|---|---|
| 사용자 요구 | 추천 5개 내부 포함, 기존 지침, 점수·보고서, API, 다중 플랫폼·업데이트를 명시 | 설계서 1~5, 8~11절 |
| 라이선스 | 고정 ref의 공식 파일 6개를 읽고 본문의 Git blob SHA를 재계산해 6개 모두 일치 | 외부 license-review.json·design-verification.json 기록 |
| 가중치 | 5개 프로필에 5축이 있고 각 행 합은 100 | 설계서 6.1절과 계산 검증 |
| 고유 항목 | 22개 family_id가 서로 다름 | 설계서 6.2절과 중복 검사 |
| 결측값 | unknown·해당 없음, 점수·측정 범위·결측 상하한을 구분 | 설계서 6.2~6.3절 |
| 실제 성과 | 색인·클릭·AI 인용·정확성을 준비도와 별도 기록 | 설계서 7절 |
| 보고서 | 문제·근거·점수·해결·검증·상태를 표로 연결 | 설계서 8절 |
| 설치·업데이트 | 공통 번들, 호스트 어댑터, 관리 설치의 readback과 복원 계약 | 설계서 10절 |
| 완료 경계 | 제품 코드·설치·API 실측·호스트 호출·공개 게시를 다음 단계로 명시 | 설계서 12~13절 |

## 2. 발견해 수정한 문제

| 문제 | 수정 | 의미 |
|---|---|---|
| 준비도 표에 실제 색인 상태가 섞임 | 점수 항목에서 제외하고 실제 성과로 이동 | 로컬 수정 직후에 검색엔진의 색인이 바뀌었다고 표시하지 않음 |
| 실제 방문 자료의 존재가 항목 적용 조건처럼 읽힘 | 성능 항목은 자료가 없으면 unknown으로 유지 | 결측 성능 15점을 없애 높은 점수를 만드는 문제 방지 |
| LLMO 준비도와 실제 답변 정확성이 섞임 | 준비도는 사이트·schema, 관찰 답변은 성과 지표 | 같은 실제 결과를 두 점수에 중복 반영하지 않음 |
| family·페이지 가중치의 순서가 불명확함 | 축→적용 family→엔진·고정 페이지 단위의 분배를 명시 | 구현자가 같은 입력으로 같은 산식을 구성할 수 있음 |
| 수정 후 적용 조건을 바꿀 여지가 있음 | 사전 원자료의 같은 기준 재계산 또는 비교 불가 규칙 | 분모 변경만으로 점수가 오르는 비교 방지 |
| 내부 SKILL의 재귀 발견 | GUIDE로 변환하고 skill frontmatter 제거를 기록 | Pi 등에서 진입점이 중복 발견되지 않도록 함 |

형식 오타도 수정했다. 초기 작성본은 작업 증거 폴더의 원본 백업으로 보존했다.

## 3. 산식의 수치 대조

아래 수치는 설계의 합성 예다. 실제 웹사이트 결과가 아니다.

| 조건 | 적용 가중치 A | 측정 가중치 M | 득점 N | 관찰 점수 | 측정 범위 | 결측 범위 |
|---|---:|---:|---:|---:|---:|---|
| 일부 자료 부족 | 100 | 80 | 58 | 72.5 | 80% | 58~78 |
| 성능 자료 없음, 나머지 통과 | 100 | 85 | 85 | 100 | 85% | 85~100 |
| 핵심 정책 항목 미확인 | 100 | 94 | 94 | 100 | 94% | 94~100 |
| noindex 실패, 나머지 통과 | 100 | 100 | 94 | 94 | 100% | 94~94 |

두 번째 예는 100점만 표시하면 오해를 만든다. 보고서에는 85%의 측정 범위와 성능 미확인을 함께 표시한다. 세 번째 예는 핵심 정책이 unknown이므로 준비 완료를 표시할 수 없다. 네 번째 예는 점수가 높아도 noindex blocker를 먼저 해결해야 한다.

M=0, A>0이면 점수 null, 측정 범위 0%, 결측 범위 0~100이다. A=0이면 해당 프로필은 not_applicable이며 점수·범위는 null이다. 제품 계산기의 입력 검증과 이 경계의 실행 시험은 구현 단계에서 수행한다.

## 4. skill-judge 기준으로 본 설계 준비

최종 SKILL.md가 아직 없으므로 120점 평가를 발급하지 않는다. 다음 설계 근거를 구현 계획의 검사 항목으로 연결한다.

| 차원 | 설계에 반영한 내용 | 구현 때 확인할 내용 |
|---|---|---|
| D1 Knowledge delta | 결측 내보내기, 긍정 사례 표본, 호스트 업데이트·파일 복사의 차이 | 일반 설명을 줄이고 판단을 바꾸는 지식만 진입점에 남김 |
| D2 사고·절차 | 근거·범위·기제에 맞는 라우팅과 사전·사후 순서 | 실제 요청이 올바른 모듈과 산출물로 이어짐 |
| D3 실패 패턴 | 중복 감점, 결측=0, 학습 봇·인용 효과 혼동을 구분 | 현실적인 오류 요청에서 잘못된 완료·효과 주장을 막음 |
| D4 규격 | 공통 name·description과 호스트별 overlay 구조 | 최종 frontmatter와 발견·명시적 호출 |
| D5 점진적 읽기 | 단일 진입점과 조건별 modules·references | 모든 파일을 매번 읽지 않으며 필요한 참조를 찾음 |
| D6 자유도 | 해결 선택은 판단 가능, 계산·권한·출처는 명확한 계약 | 기능별 스크립트와 모델 판단의 경계 |
| D7 패턴 | 접수·라우팅·검증·보고의 Process와 Navigation | 실제 SKILL 본문이 과도하게 커지지 않음 |
| D8 사용성 | 무료·API·원격 전용·미접근·플랫폼 차이 경로 | 설치·보고·업데이트의 실제 실행과 행동 검증 |

## 5. 미완료 범위와 다음 단계

미완료는 구현 계획, 포함 파일의 전이 참조 검토, 패키지 제작, 오류 보정, 채점·보고 실행, 설치·호스트 호출, README 윤문, 업데이트·복원 실행, API 실측과 공개 게시다. 이 설계 검토 결과를 그 작업들의 통과 결과로 확대하지 않는다.

사용자는 작성 설계서를 검토한다. 승인 후 writing-plans로 파일 단위 계획을 작성하고 실행 방식을 확인한다. 그 뒤에 제품 구현과 설치를 진행한다.
