# optbrew 0.2.0 설계: 한 번 부르면 끝까지 가는 초보자용 감사

작성 2026-10-16. 대표 질문 라운드 Q1~Q16과 그 앞의 대화에서 정한 내용이다. 「대표 결정」은 대표가 정한 것, 「Claude 결정」은 근거를 붙여 Claude가 정한 것이다. Claude 결정은 대표가 문서 검토에서 바꿀 수 있다.

## 1. 의도와 이유

optbrew를 부른 사용자는 스킬 하나만 부른다. 그런데 2026-10-15 youthdc.com 감사(운영본 a220fee)는 이렇게 흘렀다.

- 클라우드 작업 공간에 직접 DNS가 없어, Claude가 그 자리에서 프록시 터널 전송 스크립트를 만들어 수집했다.
- 1차 측정 범위가 21.4~41.9%였다. 수집기는 기계 판정 항목만 채점하고, 내용 판단 항목과 실사용 속도(CWV)는 「모름」으로 남겼다. 「모름」은 분모에 남아 범위를 깎는다.
- 대표가 2차 라운드를 따로 요청했다. Claude가 질문 10개를 정하고 판단 항목 237건을 `host_model`로 판정해 범위가 84.9~100%가 됐다. 스킬이 원래 할 수 있던 일을 사용자가 한 번 더 시켜야 했다.
- CWV는 PSI 공용 한도가 차서 막혔고, 키 발급은 사용자 몫으로 남았다.
- 점수는 99점대였지만 실제 결함(PR #88, `<head>` 밖으로 흘러간 메타데이터)이 나왔다.

대표는 이 상황을 「사용자가 복잡한 환경을 직접 구축하고 조작해야 감사를 받는 상황」으로 보고, 그것이 별로라고 판단했다. 0.2.0의 목적은 이것을 없애는 것이다. **한 번 부르면 설계된 감사 범위가 기본으로 돈다. 사용자 계정이 꼭 필요한 것만 처음에 한 번 묻는다.**

같은 라운드에서 배포 경로(플러그인 디렉터리, claude.ai 자동 업데이트, npm 버전 게시, Codex)도 완성한다. PR #7(0.1.4 준비분)은 merge하지 않고 이 설계의 구현과 함께 한 번에 merge·출시한다(대표 결정).

## 2. 목표·비목표·반목표

**목표**

1. 스킬을 부르면 1차·2차에 해당하는 일이 한 번의 실행으로 끝난다.
2. 사용자 자료가 필요하면 시작할 때 한 번에 묻고, 초보자가 따라만 하면 되는 런북을 준다.
3. 결과 보고서는 완성도를 보여 주고, 남은 빈칸을 알려 주고, 빈칸마다 같은 깊이의 런북을 붙인다.
4. Claude Code와 Codex, 로컬과 클라우드에서 우회 스크립트 없이 돈다.
5. 플러그인 디렉터리 등록, claude.ai 자동 업데이트, npm·GitHub Release·플러그인의 버전 일치가 출시 절차로 보장된다.

**비목표**

- 실제 검색 노출·유입·AI 인용 결과를 점수에서 추정하지 않는다(지금 원칙 그대로).
- 유료 API(Anthropic·SE Ranking) 실측을 무료 감사의 필수 조건으로 만들지 않는다.
- 원격 전용 사이트를 고치지 않는다(`proposed_only` 그대로).

**반목표** (대표 결정)

- 기술적으로 다 돌아가도 **사용자가 스킬을 쓰는 데 어려움을 느끼면 실패**다. 모든 결정은 「초보자가 막히지 않는가」로 판정한다.
- 사용자가 optbrew를 쓸 때 **대표가 결제하게 되는 경로가 생기면 실패**다.

## 3. 제약

- 런타임 의존성 0개, Node 22 이상을 유지한다. 플러그인 사본은 설치 때 패키지를 받지 않는다(`skills/README.md`의 약속, 디렉터리 심사).
- 뿌리와 `skills/` 안에 `.gitattributes`를 두지 않는다(0.1.4에서 테스트로 막음).
- 유료 호출은 사용자 본인 키로만 한다. 저장소에 키 리터럴이나 기본 키를 두지 않는다(Q16, 테스트로 막음).
- 평가 버전 규칙: 감사가 내는 관찰 집합이 바뀌면 평가 버전을 올린다(0.1.2 대표 선택 C).
- 차용한 외부 문구는 라이선스 고지를 지킨다. eli5(MIT, Thariq Shihipar), caveman(Apache-2.0, Julius Brussee, NOTICE 포함).

## 5. 감사 흐름 (0.2.0)

```
호출 → [0] 환경 점검 → [1] 시작 질문 묶음(한 번) → [2] 수집 → [3] 판정 → [4] 채점 → [5] 보고서 → (승인 시) [6] 로컬 수정 → [7] 재확인
```

### [0] 환경 점검 (묻기 전에, 사용자 몰래가 아니라 결과를 시작 질문에 반영)

에이전트가 순서대로 확인하고 결과를 `RunContext.environment_probe`에 기록한다.

1. 하네스: Claude Code 로컬 / Claude Code 클라우드 / Codex 로컬 / Codex 클라우드 / 기타. (판별 방법은 Claude 결정 C3)
2. 대상 사이트 접속: 직접 DNS → 실패하면 `HTTPS_PROXY` 경유(D11) → 실패하면 원인 분류(Codex 샌드박스, 클라우드 네트워크 수준, 사이트 장애).
3. 크롬 위치(D6, C4).
4. Google 키 유무(D17). 값은 읽지 않고 존재만 본다.
5. 로컬 소스 유무와 소스 분석 도구(D5, C6).
6. 사이트맵 쪽수(D13 판단용).

### [1] 시작 질문 묶음

한 메시지로 묻는다. 순서는 고정이다.

1. 안내 수준: 초보자용 런북 / 간단히(D3).
2. URL과 목표(이미 받았으면 확인만, 지금 `intake.md` 원칙).
3. 질문 목록 10개 안팎 확인(D7).
4. 사실 목록 후보 확인(D12).
5. 사이트맵 50쪽 초과일 때만: 표본 / 상한 올림(D13).
6. **준비할 것** (D25): [0]에서 막힌 것과 없는 것만 나온다.
   - 막는 것(네트워크 허용, D14·D15): 「왜 필요한가」와 런북 전체(안내 수준에 맞춘 판). 최대 1개.
   - 채우는 것(Google 키 D16·D17, 크롬 D6, 콘솔 내보내기): 항목마다 한 줄. 「있으면 무엇이 채워지는가」와 펼치는 답(예: 「'키'라고 답하면 절차를 보여 드립니다」). 펼쳐 달라고 하면 그 런북만 보인다.
7. 「준비가 끝나면 '시작', 일부만 됐어도 '시작'」 — 준비 못 한 항목이 있어도 감사는 끝까지 간다. 빠진 칸은 보고서의 남은 일로 간다.

사용자의 답 한 번이 이 묶음 전체에 대한 답이다. 이 답은 D21의 「추가 요청 프롬프트」로 세지 않는다.

### [2] 수집

- HTTP 수집: 지금 `fetchScoped` 경계 그대로, 전송만 둘(직접 / 프록시 CONNECT). (C1)
- 렌더링: 크롬 headless + CDP. Fetch 도메인으로 범위 밖 요청을 `failRequest`하고, 렌더 중 요청도 요청 한도에 넣는다. (C2)
- 렌더 결과는 원본 HTML과 따로 증거로 저장한다(`<sha256>.render.json`: 최종 DOM, 콘솔 오류 수, 요청 목록).
- CWV: D16 순서.

### [3] 판정

- 코드 판정: 지금 10개 + 새로 3개(`internal-navigation`, `locale-links`, `render-content`). (C5)
- 모델 판정(D8): 남은 내용 항목. 판정마다 `evaluator_type: host_model`, 근거 위치(증거 파일 + 문자 범위), 한 줄 이유. 판정 절차는 `references/judging.md`에 새로 쓴다(C7).

### [4] 채점

공식 그대로(D9). 평가 버전 0.4.0(D10).

### [5] 보고서

- `report.json`, `report.md`, 새 `report.html`(D18).
