# optbrew 0.3.0 계획: 목적에 맞게 감사하고 고치게 하기

작성일 2026-10-18. 초안을 pstack interrogate(검토자 Opus, Fable, Sonnet)로 캐물은 뒤 고친 판이다. 검토 결과는 맨 아래 「검토에서 바뀐 것」에 있다. 0.2.3 설계(같은 폴더의 `2026-10-18-optbrew-0.2.3-design.md`)를 이어받는다.

## 목적과 지금의 틈

optbrew의 목적은 사이트의 검색 유입, 네이버 노출, AI 답변 인용, 브랜드 사실 정확성, 전환을 감사하고 고치는 것이다.

| # | 틈 | 근거 |
|---|---|---|
| G1 | 목표가 자유 글이다. 「전환」, 「AI 답변 인용」을 골라도 코드는 네이버 정규식(`NAVER_GOAL`) 하나만 읽는다. | `stages.mjs` `contextFrom`, `contract.schema.json` `Goal: string` |
| G2 | AI 답변 엔진(ChatGPT, Claude, Perplexity)의 검색 크롤러를 보지 않는다. `ai-crawlers.json`과 `search-crawl-policy`는 이미 그 엔진을 다룰 수 있지만 `engines`가 `['google', naver?]`로 고정되어 있다. | `stages.mjs` `contextFrom`, `crawlers.mjs`, `ai-crawlers.md` |
| G3 | 전환은 아무 검사도 없다. | 레지스트리 22개 가족 |
| G4 | 시작 질문에서 사용자가 확인한 사실(전화, 주소, 이름)을 사이트와 비교하지 않는다. `fact-consistency`는 쪽끼리만 비교한다. | `checks/fact-consistency.mjs` `PREFIX` |
| G5 | 코드 판정 문제 코드 가운데 고치는 방법이 없는 것이 많다. 보고서 「어떻게」가 「알 수 없음」이 된다. | `remediations.json` 5개, 메시지 키 `mechanism` 일부 |
| G6 | 모델이 읽는 쪽 파일에 조각마다 `evidence_sha256`·`start`·`end`가 되풀이되고 들여쓰기 JSON이다. 옛 `judge-queue.json`도 함께 쓰인다. | `stages.mjs` `queueByPage`, `writeQueuePages` |
| G7 | 10단계(고치기)는 글뿐이다. 모델이 운영체제별 해시 명령을 고르고 ChangeRecord를 손으로 쓴다. 백업이 소스 폴더에 남아 함께 배포될 수 있다. | SKILL.md 10단계 |

## 바꾸는 것

세 PR을 차례로 올린다. 평가 버전은 PR2에서 한 번만 올린다.

### PR1. 판정 쪽 파일을 가볍게 (G6)

- 쪽 파일의 조각은 `span_id`와 `text`만 남긴다. 들여쓰기 없이 쓴다. `site_chrome` 조각은 쪽마다 제 `span_id`를 그대로 두고 `site_chrome: true`만 단다.
- 옛 `judge-queue.json`을 쓰지 않는다. `judge_queue`는 쪽 폴더를 가리킨다. judging.md 1절을 새 모양으로 고친다.
- `mergeJudgments`는 그대로다(저장된 목록에서 해시와 범위를 붙인다).
- 확인: 한국어 조각 30개짜리 쪽으로 전후 바이트를 잰다.

### PR2. 목표를 코드가 읽고, 목표마다 검사를 맞춘다 (G1~G4) — 평가 0.5.0, 프로토콜 0.3.0

- `goals.mjs`: 자유 글 목표를 다섯 표준 목표(`search`, `naver`, `ai_citation`, `brand_facts`, `conversion`)로 바꾸는 한 곳. 「문의」, 「예약」, 「상담」은 전환이다. `NAVER_GOAL`을 이것으로 바꾼다. SKILL 6단계는 메뉴 이름을 그대로 쓴다.
- AI 엔진: 목표에 `ai_citation`이 있으면 `engines`에 `chatgpt`, `claude`, `perplexity`를 더한다. `search-crawl-policy`는 `engines: ["google","naver"]`로 묶고, 새 가족 `ai-crawler-policy`(축 T, 막힘 아님)가 같은 derive를 가족 이름만 바꿔 쓴다. 두 가족 모두 robots.txt가 4xx면 전부 허용으로 본다(RFC 9309).
- 전환: 새 가족 `conversion-path`(축 S, 사이트 단위 하나, 코드 판정). 감사한 쪽에서 연락 수단 하나에 닿으면 통과다. 연락 수단은 `tel:`, `sms:`, `mailto:`, 보이는 전화번호(`facts.mjs`의 전화 읽기), 카카오톡 채널(`pf.kakao.com`), 카카오 오픈채팅, 네이버 톡톡(`talk.naver.com`), 네이버 예약(`booking.naver.com`), 문의·상담·예약 쪽 링크다. 아무것도 없고 렌더링이 필요한 사이트면 `unknown`, 아니면 `fail`. 목표에 `conversion`이 없으면 적용 대상 아님. 전화번호를 사실과 비교하지 않는다(`fact-consistency` 몫).
- 확인한 사실: `fact-consistency`가 시작 질문에서 확인한 사실(`answers.facts`)과 쪽의 값을 비교한다. 다르면 실패 문제 하나. 휴대폰 `tel:` 예외는 지금 규칙을 따른다.
- 네이버 소유 확인 메타는 점수에 넣지 않는다. 네이버가 대상이고 메타도 네이버 내보내기 파일도 없으면 「남은 일」에 서치어드바이저 등록 런북을 단다.
- 레지스트리 가족 수 22를 박아 둔 곳(`weights.mjs`, 테스트)과 고정 픽스처를 함께 고친다.

### PR3. 고치는 방법과 고치기 도우미 (G5, G7)

- 고치는 방법은 메시지 키마다 단다(`<key>.mechanism`, `.validation`, `.effort`, `.location_hint`). 테스트는 레지스트리 check 블록의 모든 `message_keys`가 방법을 가지는지 본다.
- `report.md` 옆에 `fixes.md`를 쓴다: 열린 고칠 것마다 finding_id, 쪽, 문제, 방법, 확인 방법, 위치 힌트. `composed.fixes`에서 만든다.
- `cli.mjs change start --out <OUT> --root <소스 폴더> --path <파일> --finding <id>`: 파일을 `<OUT>/changes/backup/`에 한 번만 복사한다(이미 있으면 거절). 경로는 소스 폴더 안이어야 한다. `change finish --out <OUT> --path <파일>`: 백업과 지금 파일의 해시로 완전한 ChangeRecord를 쓴다. 바뀐 것이 없으면 거절한다. SKILL 10단계의 해시 명령과 손으로 쓰는 JSON을 이것으로 바꾼다.

## 하지 않는 것

- 고칠 것 순서를 목표로 바꾸는 일(초안 PR5). 기본 목표가 거의 모든 가족을 덮어 바뀌는 것이 적고, 레지스트리 해시만 흔든다. 다음 판에서 점수 가중치로 다시 본다.
- ChangeRecord를 보고서가 읽는 일. 11단계의 비교는 그대로 다시 감사로 한다.
- 유료 API, 공개 게시, 검색엔진 제출, llms.txt 점수.
- 배포. 0.2.3 미배포분과 함께 코디네이터가 한다.

## 확인

- PR마다 단위 테스트, `npm test`, CI(Ubuntu, Windows).
- PR2: 한국 소상공인 사이트 모양의 음성 사례(카카오만 있는 문의, 글로만 쓴 전화번호, robots.txt 없음, 네이버 파일 인증)를 픽스처로 둔다.
- PR3: 임시 폴더에서 start·finish로 기록을 만들고, 두 번째 start와 바뀌지 않은 finish가 거절되는지 본다.
